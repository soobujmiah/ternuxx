# Native NPU inference

**Current status (2026-10-24):** Ternuxx has an experimental, integrated Native Termux HTP0 path for SM8735 using the official MIT-licensed llama.cpp Snapdragon release `b11849`. Runtime discovery and repeated bounded Q4_0 inference prove HTP delegation, output correctness for the tested prompts, and clean cancellation/restart. This is device-specific and **not release-qualified**: the managed Ternuxx operation currently accepts only its pinned Qwen3 0.6B model. Separate direct-runtime reference checks covered Qwen2.5 1.5B Q4_0; neither check adds arbitrary-model selection to the API. Both tested 0.6B and 1.5B workloads were slower than CPU, and sustained thermal, memory-pressure, model coverage, and broader operator correctness remain open.

A repeated 64-token HTP sequence completed two calls, then stopped before call three after post-call CPU/GPU/HTP sensor readings exceeded conservative test guards. A later single-call attempt used an active sampler and sent SIGINT at a CPU-zone reading of 61.6°C; the cancellation path cleaned up the inference child. The two completed calls proved 29/29 offload, a 319.96 MiB HTP model buffer, and no silent fallback. The device-specific readings and limits are in the [repeated resource report](../evidence/2026-10-24-p12-native-repeated-resource-check.md). This observation leaves sustained HTP stability unqualified; it is not evidence of an OEM thermal limit or proof of throttling.

The Native CLI has no verified Android thermal-status/headroom bridge: Termux's private `libandroid.so` lacks the NDK symbols, and loading the system library fails on an unavailable `libbinder_ndk.so` dependency. Keep sampled sysfs values as test observations only. See the [thermal API access check](../evidence/2026-10-24-native-thermal-api-access-check.md); do not copy system libraries or bypass the app linker namespace.

The implementation is owned by Ternuxx (`lib/npu_inference.py`) and exposed through CLI, TUI, Web, GTK, and the shared management service. It installs only selected files from a SHA-256-pinned release archive under `$HOME/.local/share/ternuxx/artifacts/`; status and execution re-hash every selected executable/library/license against the private install manifest, and same-size tampering is rejected. It never copies Android system/vendor libraries. The child runtime receives a fixed per-process loader and DSP path, explicitly selects the HVX-only HTP matmul route (`GGML_HEXAGON_MM_SELECT=1`), disables flash attention (`GGML_HEXAGON_FA_SELECT=0`), and must report complete layer offload plus a positive HTP model buffer. Any missing device, incomplete offload, invalid output, or runtime error fails without CPU/Vulkan fallback. The runtime is SoC-gated to `SM8735`.

The verified known-answer workload uses the pinned Qwen3 0.6B Q4_0 model and returns `2 + 2 = 4`; three consecutive HTP runs passed with 29/29 layers offloaded. Qwen2.5 1.5B Q4_0 returned `4` across CPU and HTP reference runs, with repeated HTP runs also passing 29/29. The observed HTP generation rates (about 9.5–10.2 tokens/s) were lower than CPU for the tested short prompts. A bounded SIGINT cancellation exited 130, logged HTP session closure, and was followed by a successful restart. The [runtime-integrity follow-up](../evidence/2026-10-24-p12-htp-runtime-integrity-followup.md) verifies that later status and execution checks detect same-size runtime tampering and records a fresh bounded Native run. See also [P12 live evidence](../evidence/2026-10-24-native-acceleration-live-check.md) and [the implementation review](../evidence/2026-10-24-p12-ternux-htp-path-review.md).

To inspect and enable the private runtime, use `tx ai npu status`, `tx ai npu runtime preview`, then `tx ai npu runtime apply --plan-id PLAN_ID --confirm INSTALL`. In interactive mode, `tx ai npu runtime apply` guides the preview and typed confirmation. Run a bounded prompt explicitly with `tx ai run --backend npu`; never infer NPU use from Vulkan graphics or device detection alone. The same preview, explicit install confirmation, status, and run actions are available in TUI, Web, and GTK. The package is experimental; do not use it for latency or battery-sensitive work without device-specific testing.

## Automatic backend priority

`tx ai run` now defaults to `--backend auto`. The shared service probes HTP0 first, then Vulkan, and selects CPU only when neither accelerator probe reports a usable backend. The chosen backend and probe failures are returned with successful results. Explicit `--backend cpu|vulkan|npu` remains available. Automatic selection happens before inference; if a selected accelerator run fails or reports incomplete offload, it fails visibly and does not retry the prompt elsewhere. This avoids duplicate work and makes backend failures measurable. TUI, Web, and GTK expose the same preference as a separate bounded local inference action.

The selector's priority and fail-closed behavior have fixture/service tests; a live default-auto inference run is still unqualified because Ternuxx's pinned Qwen3 model is absent from its private model directory. The guided installer now offers a preview-first CPU/Vulkan/HTP0 multi-select and binds the optional HTP archive preview to its single combined approval. It defaults to HTP0 on SM8735, otherwise Vulkan when the Native GPU probe succeeds, otherwise CPU; selecting HTP0 also includes the CPU fallback. This installer path has fixture coverage but has not been exercised as a fresh on-device install. The reproducible b11849 internal candidate is documented in [the P12 build evidence](../evidence/2026-10-30-p12-htp-reproducible-build-preparation.md); it is not a public release and has not been installed as a candidate on device. The currently selected installer pin remains the upstream b11849 archive.

## Historical feasibility review (superseded by the current implementation above)

The following sections preserve the initial investigation snapshots gathered before the Native loader configuration and Ternuxx HTP integration were complete. Their `unavailable`, `not implemented`, and “do not retry” statements describe those earlier tests only; they are not the current state.

## Initial device observation

In the initial pre-integration probe, the then-installed `llama-cli --list-devices` reported `(none)`. The probe found no candidate FastRPC nodes, while workspace access to enumerate `/dev` was denied; node absence was therefore unknown. That probe did not establish a DSP session and was superseded by the later pinned HTP runtime and workload evidence in the current status section. See the [fresh acceleration live check](../evidence/2026-10-24-native-acceleration-live-check.md) and [Native profile report](reports/2026-10-24-native-profile-25053RT47C.md).

Upstream llama.cpp documents a Snapdragon build containing both OpenCL and Hexagon backends, device selection such as `HTP0`, and a GPU-layer offload log. Its example uses the Qualcomm Snapdragon toolchain and ships a standalone Android package; it does not document a Termux package or certify this app sandbox. The backend is described as experimental. See the [upstream Snapdragon backend guide](https://github.com/ggml-org/llama.cpp/blob/master/docs/backend/snapdragon/README.md).

In the initial direct-runtime feasibility test, the matching upstream GitHub release artifact was tested on this device: `llama-b11849-bin-android-arm64-snapdragon.tar.gz` (release `b11849`, published 2026-10-24; SHA-256 `2d0f1a989a8f0c4329839c3bb85b6fb70edb03e0b017fee0be4cf55b7ece8f6c`). The binary starts and reports build 11849, but `--list-devices` reports no device. OpenCL reports no platform, and Hexagon fails to load `/vendor/lib64/libcdsprpc.so` because the required `libbinder_ndk.so` cannot be resolved in the Native app linker namespace. The archive is retained locally at `$HOME/.local/share/ternuxx/artifacts/llama.cpp-snapdragon-b11849/` for repeat testing; it was not installed into `$PREFIX`, and no NPU model was run. This direct test showed that invoking the upstream Android artifact without Ternuxx's runtime setup was insufficient in that environment; the later Ternuxx-owned integration and its limits are documented above. Do not work around Android linker boundaries by copying system libraries or changing global loader configuration.

At the time of the initial feasibility review, a bounded Termux package-index search found no QNN, SNPE, or Hexagon runtime package; that dated index result did not prove that no third-party runtime existed. Owner-provided QNN model/log/output artifacts showed historical graph messages for SM8735 and successful UNet/decoder calls, but lacked a reproducible command, complete pipeline timing, and independent correctness comparison. Those artifacts were research leads only. Ternuxx later added the experimental HTP implementation described above; the open sustained-qualification limits still apply. An upstream Termux issue reports Hexagon session trouble and an unsupported user-specific copied-library workaround: [llama.cpp issue #27677](https://github.com/ggml-org/llama.cpp/issues/27677).

## Historical preimplementation requirements (superseded by the implementation above)

1. The investigation confirmed the exact SoC/DSP architecture and the upstream Hexagon backend support relevant to the device.
2. It identified and audited a pinned, MIT-licensed Snapdragon runtime path, its selected files, and the Native Termux execution boundary.
3. The implementation demonstrated DSP session access from the Native Termux process without root, Shizuku, broad mounts, copied system libraries, or global loader-path changes.
4. The named workload passed bounded delegation, reference-output, cancellation, and repeat checks; sustained memory/thermal behavior and broader model/operator coverage remain open as listed above.
5. Current support claims remain exact-device and experimental; silicon detection, package presence, and external Android/PRoot results alone do not establish workload support.

Older research about the independent Ternux guest is historical context and does not establish a Ternuxx Native adapter or capability.


## Reusable owner research: Ternux and LAI

The owner's `soobujmiah/ternux` and `soobujmiah/lai` repositories contain useful, more specific historical evidence than the older general Android ecosystem research. These external results remain separate from Ternuxx's current experimental implementation documented above.

- Ternux's [`experiments/qnn-native` record](https://github.com/soobujmiah/ternux/blob/main/experiments/qnn-native/README.md) documents a small Android/Bionic QNN helper built with the pinned NDK. On the same SM8735 device, it discovered providers, created the HTP backend/device, loaded QNN model contexts, and executed the VAE encoder graph twice with repeatable outputs. The successful device route used `/system/bin/linker64` and a licensed Qualcomm runtime extracted to scratch. The record explicitly says this is not llama.cpp integration, full image correctness, or an installable extension; some work was launched from Debian PRoot, so it is not proof that a normal Native Termux command already works.
- LAI's [Hexagon qualification record](https://github.com/soobujmiah/lai/blob/main/docs/device-results/2026-09-04-redmi-turbo-4-pro-hexagon-htp-qualify-pass.md) and [repeatability/quantization follow-up](https://github.com/soobujmiah/lai/blob/main/docs/device-results/2026-09-04-redmi-turbo-4-pro-hexagon-reproducibility-and-quant-limit.md) report two real DSP-backed generations on SM8735 using `llama-hexagon`, with vendor FastRPC traces and HTP hardware information. That path ran inside LAI's Android app packaging and runtime lifecycle. It supports the conclusion that this phone can run a sandboxed third-party HTP workload; it does not show that the upstream standalone Snapdragon archive can resolve the same libraries from Termux's linker namespace.
- LAI's [native Android lessons](https://github.com/soobujmiah/lai/blob/main/docs/research/2026-10-13-native-android-hexagon-lessons-from-proot.md) and [corrected ecosystem research](https://github.com/soobujmiah/lai/blob/main/docs/HANDOFF-2026-09-03-npu-android-ecosystem-research.md) point to QNN's app-private runtime/session setup as the better-supported integration lead. They also warn that raw FastRPC device-node access and `ggml-hexagon`'s direct loading route can fail under app SELinux/linker restrictions. Do not generalize a PRoot result into Native Termux support.

### Ternux experimental brokered HTP path — external evidence

The owner's Ternux `main` branch was rechecked on 2026-10-24; its head remains `9fda63162426f77ee575b5f6729d8799a30f51b7`. Its [experimental HTP guide](https://github.com/soobujmiah/ternux/blob/9fda63162426f77ee575b5f6729d8799a30f51b7/guides/llama-htp-experimental.md) and [single accelerator release plan](https://github.com/soobujmiah/ternux/blob/9fda63162426f77ee575b5f6729d8799a30f51b7/docs/ACCELERATOR-RELEASE-PLAN.md) describe a Linux ARM64 llama.cpp package using a Ternux Binder/FastRPC broker. Exact workflow artifact `38560288558` passed isolated-HOME installation, returned the known answer `4`, assigned all 31 model layers to HTP0, exited 0, and closed the DSP session cleanly. Its bounded SIGINT check exited 130 after child shutdown and clean session close. This is stronger same-device evidence for a brokered PRoot-to-HTP route than the standalone Android `b11849` archive, whose Native linker failure is recorded above.

The route remains experimental and external to Ternuxx. On the same device, HMX `MUL_MAT` had 529 infinite-error failures; the explicitly selected HVX flash-attention suite had seven reproducible numerical errors; a broad HVX run had 45 numerical failures and aborted after a DSP queue error. The package provides no automatic CPU/Vulkan fallback, and the guide leaves restart, other models, and sustained operation unqualified. Do not classify these Ternux results as Ternuxx support or import its source/artifacts or lifecycle. They establish a concrete research direction: assess a separately implemented, least-privilege Android broker client and exercise only correctness-qualified HTP operators behind an explicit experimental opt-in.

These external Ternux and LAI routes remain separate from Ternuxx. Their historical results cannot qualify this implementation; current Ternuxx status and remaining acceptance gates are recorded at the top of this document and in the [active P12 phase](../PHASE-STATUS.md).
