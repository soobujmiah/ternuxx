# Native SSH connection and lifecycle contract

Native Termux owns SSH and recovery. No guest provider is part of the current Ternuxx product. Port 8022 is the owner's development channel and is inspection-only for Ternuxx lifecycle. Port 8023 is the separate loopback-only `ternuxx-sshd` product service. Preserve both channels during repository work.

[Client coverage](CAPABILITY-MATRIX.md), [phase state](../../project/phase-state.json), and [the repository audit](../audit/REPOSITORY-AUDIT.md) own current progress. The earlier combined design/runtime narrative is preserved in [dated history](history/2026-10-22-ssh-lifecycle.md); its old daemon, password, PID, listener-correlation and command-name claims are historical.

## Implemented behavior

`tx ssh inspect` is the single shared read-only SSH diagnostics operation across the CLI, TUI, Web and GTK clients. It reports redacted configuration, service/process identity, effective bind/auth policy and bounded loopback banner reachability. It does not read credential files, expose raw config or authenticate. `tx ssh keys-list` is separate and read-only: it first runs bounded read-only `sshd -T` for the managed loopback login context and refuses paths other than `.ssh/authorized_keys`; it then reads that fixed `$HOME/.ssh/authorized_keys` file after ownership, type, symlink and size checks, and returns public-key type, SHA-256 fingerprint and sanitized comment. A 2026-10-22 inspection found both managed 8023 and 8022 configs resolved `AuthorizedKeysFile` to `.ssh/authorized_keys`, so this was a shared Termux-account inventory, not an 8023-only credential store; recheck live config before relying on it. It never returns key bytes, private material or password data. CLI, TUI, Web and GTK expose this inventory through the shared service; the Web session additionally requires the separate `ssh.credentials.read` capability. Procfs and SOCK_DIAG listener observations are separate; restricted visibility remains unknown.

`tx ssh start|stop|restart` first previews the exact fixed service. Apply requires `--yes --plan-id PLAN_ID`, rechecks definition/manager/state identity and journals before Runit control. Restart always requires confirmation, sends down then up to the one fixed unit, and warns that active 8023 clients may disconnect. All four clients expose scoped managed-8023 status/start/stop/restart through the common service. A catalog entry alone is not a client action.

`lib/runit_deployment.py` separately reconciles the fixed run definition using a validated plan, private backup and rollback. Definition replacement does not restart a daemon or change SSH config. Public-key enrollment/revocation source operations are available through CLI, authenticated Web, TUI and GTK. Preview-confirmed Native Ed25519 client-key creation is also available in all four clients; it writes only to `.ssh/ternuxx-keys`, refuses existing targets, uses 0600 private-file permissions, returns no private bytes, and leaves enrollment as a separate shared-account action. The key is unencrypted, which each creation flow discloses. The 2026-10-22 Native GTK source/build/install identity check passed; its creation dialog still needs visual review. Password recovery decision, general connection profiles, authenticated post-action readiness, caller-session correlation and cold-boot verification remain incomplete. On 2026-10-22, the Native key manager passed isolated disposable enrollment, revocation, recovery-key authentication and last-key refusal against a temporary loopback sshd; see [qualification evidence](../evidence/2026-10-22-ssh-disposable-auth-qualification.md). Managed SSH Wake Lock now has a shared preview-confirmed next-start preference in CLI, TUI, Web and GTK; it defaults enabled, leaves the running process/lease untouched, and does not claim Android-global lock state. The 2026-10-22 evidence records source/installed service-wrapper parity; see [Wake Lock policy evidence](../evidence/2026-10-22-managed-ssh-wakelock-policy.md). See [key generation evidence](../evidence/2026-10-22-ssh-client-key-generation.md).

A 2026-10-22 Native inspection reported the 8023 loopback service running with valid configuration, verified process/definition identity, a protocol banner and effective `AuthenticationMethods publickey`; `PasswordAuthentication` and keyboard-interactive authentication were disabled. A historical 2026-10-22 PRoot client test authenticated to 127.0.0.1:8023 using its existing configured key and strict host-key verification; this predates the 2026-10-23 service-wrapper repair, and authenticated access after that repair remains unverified. See [recovery evidence](../evidence/2026-10-22-ssh-8023-key-recovery.md). For that already-configured client, `ssh -p 8023 termux` is the verified recovery route. Password login is not a recovery route. That dated test proves only local PRoot-to-Native access at the time; it is not a current supported client. 8023 remains loopback-only. Kernel listener-to-process correlation remains unknown when Android denies both observation paths. [RB08](../evidence/2026-10-22-p3-rb08-postboot-exit-audit.md) records its separately dated authenticated check.

## Identity and credential requirements

Keep the Native Termux account, SSH client key, SSH server host key, management session and guest account distinct. Client private keys stay with their client; the server receives only public authorization material. A management login is not SSH login proof, and an SSH login is not automatic API authorization.

Key enrollment/removal and Native client-key generation now have typed shared-service operations in source. Recovery-key creation is preview-confirmed unencrypted Ed25519 under the Native SSH key directory; TUI creation offers a separate preview/confirmation for enrolling the resulting public key. The standalone TUI enroll action can also select an existing Native `.pub` file. Disposable end-to-end enrollment/authentication behavior is qualified against a temporary Native sshd, and durable exact rollback now restores saved before-state only if the live target still matches. Disposable credentials were used; no production key was enrolled or revoked. Production credential changes still require a separately verified plan and owner-visible confirmation. Never overwrite an existing key, rotate host identity implicitly, log private material or export credentials into repository/evidence/ordinary backups.

The existing 8022 and 8023 endpoints share one Termux account. A password reset or shared authorized_keys edit can affect both endpoints. A credential preview must identify that impact; it cannot describe an account-wide change as 8023-only. Protect the current development identity and retain a proven local recovery path. A future separately scoped authorized-key file requires an explicit, validated managed-config migration.

A lost private key is not recoverable from its public key. Recovery needs a working authorized client or local Termux access to enroll a replacement. Do not suggest password recovery when effective service policy rejects passwords. Auth policy is discovered live and preserved until replacement access is verified.

If new private material is explicitly requested, use a new unused private destination and a protected reference; distinguish file permissions from hardware-backed storage. No secrets in command arguments, URLs, public logs, screenshots, journal payloads or Git.

## Shared service and lifecycle rules

CLI, guided TUI, authenticated loopback Web and GTK use the same typed management contracts. Clients do not write configs, keys or boot files directly. There is no arbitrary-command endpoint. Native control remains available without PRoot or a graphical client.

A future setup/migration plan must identify provider, principal, endpoint, current ownership, selected auth, host identity, affected sessions, boot/Wake Lock effects, rollback and exact owned paths. Validate a separately staged config with sshd and a bounded authenticated candidate connection before cutover. Unknown ownership, endpoint conflicts, failed auth or ambiguous identity blocks mutation. Never stop an external daemon to make validation possible.

Stop/restart must account for the caller's access path and preserve an out-of-band recovery route or obtain explicit acknowledgement of the exact disconnect. Journal before mutation; repeated requests must not duplicate daemons, authorization entries, boot hooks or Wake Lock owners. Broader setup/recovery and remote-access scope remain planned.

## Boot, Wake Lock and continuity

The installed Native service boot helper starts the official Runit supervisor and checks managed SSH readiness. It does not enter PRoot. Managed SSH now has a shared preview/apply automatic-start preference backed by the fixed Termux Runit `down` marker. It affects the next supervisor start only; live start/stop actions are separate. The 2026-10-22 Native read-only preview verified the enabled policy and confirmed no marker/process change. The current run script acquires the `native.sshd` lease; managed SSH has a preview/apply next-start Wake Lock preference that does not alter the running lease. Android cold-boot delivery remains unverified. See [startup policy evidence](../evidence/2026-10-22-ssh-service-autostart-policy.md) and [Wake Lock policy evidence](../evidence/2026-10-22-managed-ssh-wakelock-policy.md). A proposal's “never by default” policy is not the current installed behavior.

Wake Lock accounting is owned by `lib/wakelock_manager.py`. A workload may release only its own lease; stopping a guest cannot release Native SSH's lease. Android's app-global holder state can remain unknown even when Ternuxx accounting is verified.

[Continuity implementation](CONTINUITY-IMPLEMENTATION.md) distinguishes boot observations, current readiness and private checkpoints. No agent/task resumes automatically. Existing rootfs, host identity, working clients and owner-managed 8022 remain preserved.
