# ADR-0003: Separate generated repository state from SKB knowledge return
> **Scope update (2026-10-24):** ADR-0017 recorded a temporary Native-only direction, later reversed when the owner reauthorized Debian PRoot support. This record remains historical; current behavior is defined by source, [P11 phase status](../../PHASE-STATUS.md), and [restoration evidence](../../evidence/2026-10-24-p11-proot-source-restoration-audit.md).

- **Date:** 2026-10-17
- **Status:** accepted
- **Type:** cli-tool

## Context

The owner wants phase documents and repository status to update automatically, and durable project knowledge to return to the canonical SKB knowledge base. SKB defines a pull-only registry: a participant updates its own deterministic `.repo/` state; SKB reads state only from explicitly registered repositories. Human-authored technical findings remain separate from mechanically derived commit and CI state.

## Decision

Keep three sources of truth: project-authored technical/evidence docs, phase progress in `project/phase-state.json` rendered by `tools/phase_docs.py`, and Git/CI facts under `.repo/` generated by SKB `tools/repo_knowledge`. Agents separately return verified durable knowledge to the canonical SKB file. CI receives no SKB write credential and never mirrors arbitrary project files into SKB.

## Alternatives considered

- **One all-purpose generated status document:** rejected; it would mix human judgement, phase state, and CI facts and drift from their owners.
- **Project CI pushes to SKB:** rejected; it creates a cross-repository credential and bypasses SKB's allowlisted pull/registration model.
- **Hand-copy commit/build facts into README or SKB prose:** rejected; duplicate mechanical facts become stale and can contradict authoritative state.

## Rationale

The pull-only contract limits credentials and makes registry membership explicit. Distinct generated and human-authored records keep attribution and evidence boundaries clear.

## Trade-offs

SKB's deterministic registry update is not instantaneous and requires repository readiness, owner approval, registration, and the configured reader integration. Durable knowledge return remains a content-reviewed session responsibility.

## Consequences

- Vendor the exact SKB repo-state tooling and schemas during the onboarding implementation.
- CI updates only this repository's `.repo/` using a same-repository token with least privilege.
- Do not hand-edit `.repo/` files or phase-generated blocks.
- Before registration, pass the SKB new-repository readiness gate; keep project evidence internal and exclude public projection.
